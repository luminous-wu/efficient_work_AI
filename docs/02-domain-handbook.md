# 02 · 领域实战手册：链接脚本 / 内存布局 / AUTOSAR

本章是"查用型"文档。12 个场景按真实工作流排序，每个给出：**何时用 → AI 扮演哪个角色 → 怎么提（精简提示骨架）→ 验证要点（必看）**。

> 所有提示均假设你已套用第 01 章的"四要素 + 禁猜规则 + 脱敏"，下面只写场景特有部分。完整可复制模板见 `prompts/`。

---

## A. 理解与建模类（信任度高，最划算先用起来）

### 场景 1 · 读懂一份陌生/第三方链接脚本
**何时**：接手新平台、看供应商交付的 .ld/.lsl/.dld，或读 MCU 厂商 demo 脚本。
**角色**：① 翻译官。
**提示骨架**：
```
逐段讲解这份链接脚本：每个 MEMORY/region 是什么物理存储、每个 section 放什么、
LMA 与 VMA 是否不同（即是否需启动期拷贝）。用一张表输出：
段名 | 归属region | 内容类型 | LMA | VMA | 是否需拷贝/清零 | 我需向手册确认的点
末尾列出"这份脚本隐含了哪些关于该 MCU 内存模型的假设"。
```
**验证**：表里每个"内容类型/是否拷贝"的判断，对照 `objdump -h` 实际段属性核一遍；"隐含假设"逐条回查手册。

### 场景 2 · 建立某 MCU 的内存模型心智图
**何时**：上新芯片（如从 S32 转 AURIX），需要快速建立 PFLASH/DFLASH/PSPR/DSPR/LMU/cached vs non-cached 的全貌。
**角色**：① + ②（讲解 + 指路该读手册哪节）。
**提示骨架**：
```
我要建立"某 TriCore 类三核 MCU"的内存模型心智图（不要给具体地址，给结构与原理）：
- 各类存储（程序闪存/数据闪存/各核本地 scratchpad/全局共享 RAM）的用途与典型取舍
- "同一物理 RAM 的缓存别名地址 vs 非缓存别名地址"机制及对链接脚本的影响
- 多核场景下"哪些数据必须放各核本地、为什么"
输出：分层结构图（文字）+ 一张"决策：什么数据该放哪、依据什么"对照表。
最后列出我应在该芯片数据手册中精读的章节主题清单。
```
**验证**：心智图是脚手架，不是事实源。拿"章节主题清单"去翻真实手册逐节确认；地址永远查手册。

### 场景 3 · 跨编译器/链接器语义翻译
**何时**：项目从 GHS 切 TASKING、或参考 GNU ld 资料但工程用 .lsl，需要语义对应。
**角色**：① 翻译官（本方向最安全高效的用法之一——你两边可交叉验证）。
**提示骨架**：
```
把下面这段 <源链接器，如 GNU ld> 片段，翻译成 <目标链接器，如 TASKING LSL> 的等价写法。
逐构造对应：MEMORY/region、SECTIONS、ALIGN、LMA/load-time-relocation、KEEP/不丢弃、
段填充、符号定义。对每条给出"两者语义差异/陷阱"。不确定的语法标 <<CONFIRM:手册>>。
```
**验证**：翻译后的目标脚本**必须实际链接 + 比对两边 .map 段布局一致**，不能只看"读起来对"。

## B. 起草与修改类（信任度低，必走验证闭环）

### 场景 4 · 新增一个内存段 / region
**何时**：要为新功能加诊断缓冲、共享区、标定区等。
**角色**：③ 草稿手。
**提示骨架**：
```
现有片段（脱敏）：<粘贴>
需求：新增一段"核间非缓存共享区"，名 SharedNc，大小 <我给值或标占位>，对齐 <值>。
要求：1) 给出最小改动 diff，每行注释；2) 地址若我未给，用 <<CONFIRM:datasheet>> 占位，禁止猜；
3) 给出我应在 .map 断言的 3 条验证条件；4) 提示该段在多核一致性上的注意事项。
```
**验证**：清单全过——地址查手册、.map 断言段位置与无重叠、`readelf -S` 看属性、确认非缓存别名地址用对、多核访问加屏障/volatile 的需求与设计一致。

### 场景 5 · 排查链接器报错 / 告警
**何时**：`region 'X' overflowed by N bytes`、`section '.y' will not fit`、对齐/重叠告警。
**角色**：④ 找茬者 + ① 讲解。
**提示骨架**：
```
链接器：<型号版本>。报错原文（脱敏）：<粘贴>
相关 .map 摘录：<粘贴 region 用量与溢出段>
请：1) 解释根因的可能集合（按概率排序）；2) 对每种给"如何用 .map 进一步定位"；
3) 给候选修复手段及各自风险（移段/裁功能/换 region/调对齐）；不替我决定，列权衡。
```
**验证**：根因要用 .map / `nm --size-sort` 实证定位，不照 AI 排序盲改；修复后重核 .map 用量与所有段位置。

### 场景 6 · 起草 / 审查启动拷贝表与清零表
**何时**：bring-up 阶段，.data 的 ROM→RAM 拷贝、.bss 清零、多核各自初始化。
**角色**：④ 审查（**不要让它从零造格式**——拷贝表格式是 MCU/启动代码强绑定的）。
**提示骨架**：
```
这是该平台启动代码使用的拷贝表条目格式（我提供，脱敏）：<粘贴结构定义>
这是链接脚本中生成拷贝表的片段：<粘贴>
请审查：1) 拷贝表覆盖的段集合 与 需在运行期可写/初始化的段集合 是否一致（列差集）；
2) 对齐/大小字段单位是否自洽；3) 多核下每核清零/拷贝是否互不遗漏不重叠；
仅指出疑点与验证方法，不臆造格式。
```
**验证**：差集逐项对照 `objdump -h`；上电后用调试器看 .data/.bss 实际值；AI 绝不能定义拷贝表二进制格式。

### 场景 7 · 安全相关内存分区（ASIL / MPU region）
**何时**：需要按功能安全做内存隔离（ASIL-B/D 分区、MPU region 与链接段对齐）。
**角色**：② 指路 + ④ 找茬（**绝不让 AI 做安全决策**）。
**提示骨架**：
```
背景（抽象）：一个需做内存隔离的多核控制器，要求安全相关数据与 QM 数据物理隔离、
受 MPU 保护。不要替我做安全决策。请：
1) 列出"链接段布局如何配合 MPU region 粒度/对齐约束"的通用工程要点清单；
2) 给一份"我做该设计时应核对的安全相关问题"自查问题集；
3) 指出常见错误模式。所有内容作为我评审的输入，最终以安全需求文档为准。
```
**验证**：100% 以项目功能安全需求 / 安全手册为准；AI 输出仅作 review checklist 输入，任何条目须能追溯到安全需求。

## C. AUTOSAR Classic 衔接类

### 场景 8 · 讲清 MemMap 与链接器 section 的映射机制
**何时**：搞不清 `*_MemMap.h` 的 `START_SEC_*` / `STOP_SEC_*` 怎么最终变成链接脚本里的段。
**角色**：① 讲解。
**提示骨架**：
```
讲清 AUTOSAR Classic 内存映射链路：模块源码 #include MemMap.h 的段宏 →
编译器 #pragma/属性 → 产生的 section 名 → 链接脚本 SECTIONS 如何归拢这些段 →
最终 region。用一张端到端追踪表（以一个 CODE 段、一个 VAR 段、一个 CONST/CALIB 段为例）。
说明不同编译器在"段宏如何落成段名"上的差异点。
```
**验证**：拿你工程里**真实一个段**端到端走一遍（grep MemMap → 看编译产物段名 → 看 .ld → 看 .map），与 AI 描述对账。

### 场景 9 · 排查"某模块变量没进预期段"
**何时**：标定量没进 CALIB 段、某 VAR 没进期望 RAM、init/no-init 错位。
**角色**：④ 找茬 + ① 讲解。
**提示骨架**：
```
现象：模块 MODULE_A 的某变量预期在 <段类别>，实际在 <段>。
我提供：该变量声明上下文（脱敏）、相关 MemMap 段宏使用、链接脚本归拢该段的片段。
列出按概率排序的原因（MemMap 配对错/段宏选错/编译器属性未生效/链接脚本通配符吞并/
include 顺序），每条给"如何最小实验验证"。
```
**验证**：用最小实验 + `objdump -h`/`nm` 实证，别照单全改。

### 场景 10 · 起草 Os / 内存相关配置片段
**何时**：需要 OS 应用、栈、各核内存相关配置的草稿（OsApplication、栈分配、内存保护边界）。
**角色**：③ 草稿手（仅出结构骨架，值留占位）。
**提示骨架**：
```
AUTOSAR Classic R<版本>。给出 <某项 Os/内存配置> 的结构骨架与各字段含义，
所有项目相关数值用 <<CONFIRM:项目配置/工具链>> 占位，禁止填默认值当真值。
附：每个字段"填错会导致什么现象"速查表，便于我配置后自检。
```
**验证**：用厂商配置工具（如 EB/Vector/厂商 OS 配置器）生成与校验为准，AI 草稿只作理解骨架。

## D. 自动化与文档类（高杠杆，最值得长期投入）

### 场景 11 · 生成内存分析 / 预算守护脚本
**何时**：想要 CI 或本地自动检查"段是否越界、region 用量、是否回退到错误内存、布局是否漂移"。
**角色**：③ 草稿手（脚本是纯软件，可单测，**这是 AI 在本方向最安全且收益最高的用法**）。
**提示骨架**：
```
写一个 Python 脚本：解析 <链接器> 的 .map（我给一段样例格式），实现：
1) 输出各 region 用量/占比，超阈值非零退出（阈值可配 yaml）；
2) 校验关键段是否落在预期 region（规则表我提供），违例报错；
3) 与上次基线 .map 对比，输出段地址/大小漂移报告。
要求：纯标准库、含 pytest 用例、对畸形输入健壮。先给解析正则的假设让我确认 .map 格式。
```
**验证**：用真实 .map 跑 + 你自己造的"已知越界"用例验证脚本能抓到；脚本逻辑你要看懂（它将成为你的安全网，不能黑箱）。
**衍生**：同法可让 AI 写 `readelf/nm` 包装、map diff 可视化、批量脱敏 `sanitize.py`。

### 场景 12 · 写文档 / 评审材料 / 知识沉淀
**何时**：给同事写内存布局说明、变更评审说明、给自己整理学习笔记。
**角色**：① + ③（结构化表达，你提供事实，它组织）。
**提示骨架**：
```
我提供事实要点（已验证）：<bullet>。请整理成 <内存布局设计说明 / 变更评审单 / 学习笔记>，
含：背景、布局总表、关键决策与依据、风险与缓解、验证方式。
只组织我给的事实，不要补充你"以为对"的技术细节；缺失处标 [需补充]。
```
**验证**：成稿里所有技术陈述都应能追溯到你给的已验证要点；`[需补充]` 处自己补，别让 AI 脑补。
