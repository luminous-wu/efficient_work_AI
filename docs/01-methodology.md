# 01 · 方法论与工作流体系

本章是整套体系的地基。它不讲"AI 能做什么"（那是第 02 章），只讲**"在链接脚本 / 内存布局这个高风险、强专业、强保密的方向，应该用什么样的协作方式让 AI 真正提效，同时不出事"**。

---

## 1. AI 的 5 种角色（明确角色才能用对）

不要笼统地"问 AI"。每次开会话前，先想清楚这次 AI 扮演哪个角色——角色决定了你怎么提问、怎么验证、信任度多高。

| 角色 | 用途 | 信任度 | 本方向典型场景 |
|---|---|---|---|
| **① 翻译官 / 讲解员** | 把陌生材料转成你能懂的心智模型 | 高（但需交叉验证概念） | 解释一段第三方 .lsl、把 GHS 链接脚本语义翻译成 GNU ld 等价物、讲清 AURIX 的 cached/non-cached 段地址映射 |
| **② 研究助理** | 收敛资料、列出"该去查哪些手册的哪几节" | 中（给方向，不给结论） | "AURIX TC3xx 多核启动时 CPU0 拷贝表的格式相关章节是哪些"、"AUTOSAR MemMap 与链接器 section 的对应机制" |
| **③ 结对工程师 / 草稿手** | 出初稿、出脚手架、出 80% 然后你改 | 低（必须逐行审 + 工具验证） | 起草一段新的 memory region、写 .map 解析脚本、生成 MISRA 风格启动代码骨架 |
| **④ 代码评审员 / 找茬者** | 让它挑你脚本/布局里的毛病和盲点 | 中（它提疑点，你定性） | "这段 linker script 在多核场景下有什么对齐/重叠风险"、"我的内存预算检查脚本漏了哪些段" |
| **⑤ 橡皮鸭 / 思辨对手** | 逼自己把方案讲清楚，暴露思维漏洞 | 不涉及事实，只涉及逻辑 | "我打算把标定数据放 DFLASH 并通过 NvM 镜像到 RAM，帮我反驳这个方案" |

> **关键纪律**：角色 ③（出代码/脚本）在本方向信任度最低。链接脚本的错误**不会编译报错也不会立刻崩**，可能上车跑几千公里后偶发踩内存。所以角色 ③ 的产物 100% 要过第 4 节的验证闭环。

## 2. 核心协作循环：D-D-V-I

每个任务都走这四步，**V（验证）不可跳过**。

```
Decompose  →  Draft  →  Verify  →  Integrate
 拆解          起草       验证        整合
```

### Decompose（拆解）— 你做，不是 AI 做
把任务拆到"单个问题边界清晰、可独立验证"的粒度。
反例："帮我写 TC3xx 三核的链接脚本" —— 太大、无法验证、必然出错。
正例：拆成 →
1. CPU0 的 PSPR/DSPR scratchpad 该映射哪个地址区间？（查手册，AI 只做角色①讲解）
2. .bss/.data 的清零/拷贝表条目格式是什么？（角色②给方向）
3. 给定区间，写出该 region 的语法骨架。（角色③出草稿）
4. 校验脚本：解析 .map，断言每个段落在预期 region 内、无重叠、对齐正确。（角色③出工具）

### Draft（起草）— AI 做
用第 3 节的提示词结构，让 AI 出**带注释、标注"此处需你确认"**的草稿。明确要求它把不确定的地址/大小留成占位符 `<<CONFIRM: from datasheet §x.x>>`，而不是猜一个看起来合理的值。

### Verify（验证）— 你做，铁律
见第 4 节。**没过验证清单的产物，不准进真实工程。**

### Integrate（整合）— 你做
把验证过的片段并入工程，并把"这次 AI 帮你建立的心智模型 / 踩的坑"沉淀进 `prompts/` 或个人笔记——让下次更快。

## 3. 提示词工程：本方向的四要素结构

通用的"提示词技巧"对本方向不够。链接脚本/内存布局必须在提示里钉死**四要素**，缺一就会得到"看起来对、实则危险"的答案：

```
[R] Role     —— 让 AI 扮演哪个角色（第1节），并声明"不确定就标占位符，禁止编造地址"
[C] Context  —— 编译器/链接器型号+版本、MCU 型号、AUTOSAR 版本、相关约束（脱敏后）
[A] Artifact —— 喂给它的权威材料：你贴的 .ld 片段 / .map 摘录 / 手册条款（脱敏）
[F] Format   —— 要求的输出格式：带行内注释、占位符标注、对照表、验证步骤清单
```

**模板（可直接用，已放进 `prompts/_skeleton.md`）：**

```
[Role] 你是嵌入式链接脚本结对工程师。规则：任何地址/大小/对齐若我未提供，
       用 <<CONFIRM:来源>> 占位，严禁猜测填值。

[Context] 编译器：TASKING VX-toolset for TriCore vX.Y；MCU：<泛化为"某三核 TriCore 类 MCU">；
          AUTOSAR Classic R<版本>；约束：CPU0 私有数据需放各核本地 scratchpad。

[Artifact] 这是我现有 .lsl 的相关片段（已脱敏）：
           <粘贴片段>

[Task] 我要新增一段非缓存的核间共享区。

[Format] 输出：1) 修改后的片段并对每行加注释；2) 一张"段→region→地址来源"对照表；
         3) 我应在 .map 中断言哪些条件来验证。
```

### 几个高杠杆技巧
- **要"对照表"而非"段落"**：内存的事用表格表达，错位一眼看出。
- **要它先复述约束再作答**：开头加"先用一句话复述你理解的约束，再开始"——能拦住 70% 的跑偏。
- **逼它给验证方法**：每个输出都附"我该如何独立验证这一条"，把验证负担显式化。
- **善用"对比/diff"任务**：AI 在"解释两段脚本差异""把 A 编译器语法翻译成 B"上最强且最安全（你有两边可交叉核对）。
- **少喂多轮**：一次给一个问题边界，链接脚本上下文一长 AI 极易把不同 region 的地址张冠李戴。

## 4. 验证纪律（本方向的生命线）

> AI 在链接脚本方向的失败模式不是"明显胡说"，而是**"语法正确、地址貌似合理、能链接通过、运行偶发出错"**。普通验证（编译通过）在这里完全无效。

### 强制验证清单（任何 AI 产出的脚本/布局并入前逐条打勾）

- [ ] **地址/大小/对齐**：每个数值都能在**数据手册 / 芯片 memory map / 厂商 SDK 头文件**中找到出处，不是 AI 给的。
- [ ] **.map 交叉核对**：链接后用 `.map` 文件断言——每个段的实际地址落在预期 region；无段间重叠；`region overflowed` 类告警为零。
- [ ] **符号检查**：`readelf -S` / `objdump -h` / `nm` 核对段名、属性（A/W/X）、加载地址 vs 运行地址（LMA vs VMA）是否符合预期（尤其 ROM→RAM 拷贝段）。
- [ ] **拷贝/清零表**：启动拷贝表、.bss 清零范围 AI 不得臆造格式——必须对照该 MCU 启动代码 / SDK 实现确认。
- [ ] **多核 / 安全分区**：涉及多核本地内存或 ASIL 内存保护（MPU region）时，与功能安全/内存保护需求文档逐项对照，AI 输出仅作清单提示。
- [ ] **对齐与 CRC/标定**：标定区、CRC 表、NvM 块的对齐与边界与对应组件需求一致。
- [ ] **回归**：改动后跑既有内存预算检查脚本 + 在目标板（或仿真）冒烟启动。

把这份清单做成你个人的 checklist 文件，每次 review 实际勾。

## 5. 保密卫生（即使个人学习也练成肌肉记忆）

你在汽车行业，"对客户保密、对供应商保密、对芯片 NDA 保密"是职业底线。**把脱敏当成习惯，而不是合规任务**——这样真到量产场景自然不会出错。

### 脱敏三原则
1. **去标识**：删客户名、项目代号、内部件号、专有符号名 → 用 `MODULE_A` / `CoreLocalData` 之类泛化名。
2. **去具体地址**：把真实地址换成相对/符号化表达，或问"机制"而非"我们的具体值"。问 *"这类 MCU 的 scratchpad 通常如何在链接脚本中映射"* 而非 *"我们项目把 X 放在 0x70000000 对不对"*。
3. **去场景**：把"我们这个区域控制器的某功能"抽象成"一个有 N 核、需做 ASIL-B 内存隔离的控制器"。

### 实操
- 建一个本地脚本 `sanitize.py`（见 `03-tooling-setup.md`），贴脚本前先跑替换：客户名→`CUST`、地址→`0xADDR_n`、私有符号→`SYM_n`，并保留一张本地映射表供你自己还原。
- **能问"原理"就不问"我的代码"**。链接脚本方向 80% 的学习需求是"理解机制"，不需要贴真实工程。
- 真需要贴片段时，只贴**最小可复现片段**且脱敏。

## 6. 反模式（这些一定别做）

| 反模式 | 为什么危险 | 正确做法 |
|---|---|---|
| 让 AI 直接生成完整可量产链接脚本 | 地址必然有臆造，且错误隐蔽 | 拆解→片段草稿→工具验证（第2节） |
| 信任 AI 给出的具体地址/寄存器值 | 训练数据里不同芯片混杂，张冠李戴 | 一律以数据手册为准，AI 只标占位符 |
| 一个长会话里混问多颗 MCU / 多个编译器 | 上下文污染，地址互窜 | 一会话一目标，明确 Context 四要素 |
| 用"编译通过"当验证 | 链接脚本错误不报编译错 | 走第 4 节 .map/readelf 验证闭环 |
| 把"AI 讲的机制"当权威结论引用进设计文档 | 概念可能似是而非 | 角色①②的产出需回查标准/手册再落文档 |
| 贴未脱敏的客户/项目代码 | 职业与合规风险 | 第 5 节脱敏卫生 |

## 7. 一页纸总结（贴显示器边上）

```
开会话前： 选角色(1/2/3/4/5) → 想清这次信任度多高
提问时：   R 角色+禁猜规则  C 型号版本约束  A 脱敏材料  F 表格+占位符+验证步骤
产出后：   走 D-D-V-I，V(验证清单)绝不跳，地址只信手册和 .map
贴材料前： sanitize 三原则，能问原理不问我的代码
心态：     AI 放大判断力，不产生判断力。判断力靠 04 路线图自己长。
```
